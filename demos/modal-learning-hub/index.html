Section 01

The Modal Platform

One runtime, five product surfaces: CPU/GPU containers that start in seconds and bill by the second

Five Products, One Container Runtime

Product 1

Sandboxes

Containers defined at runtime for untrusted or agent code. gVisor or VM isolation, egress control, snapshots, sidecars.

~8 guide pages · V2 backend default since SDK 1.6

Product 2

Functions & Batch

Decorate Python, deploy, call .remote()/.map(). Autoscaling, cron, web endpoints, Servers.

~40 guide pages · the original Modal

Product 3

Endpoints

Managed LLM inference from the Model Library or your weights. OpenAI/Anthropic-compatible. Shared (per-token) or Dedicated.

New in 2026 · modal endpoint CLI

Product 4

Training

Fine-tune, RL, eval on GPUs that spin up in seconds. Tinker-compatible API, multi-node clusters.

T4 → B300 · @modal.clustered()

Product 5

Notebooks

Hosted notebooks on Modal compute, priced like Sandboxes. Idle auto-stop, GPU attach.

Sandbox pricing tier

Section 02 · Sandboxes

Sandboxes

Runtime-defined containers for untrusted code · gVisor or KVM · 5-min default lifetime, up to 24h · the primitive AgentVetter is built on

Hello, Sandbox

scan_one.py — runs with plain python, no modal run
import modal

app = modal.App.lookup("agentvetter", create_if_missing=True)
image = modal.Image.from_name("agentvetter-scanners")  # pre-built, see Images

sb = modal.Sandbox.create(
    app=app, image=image,
    timeout=10 * 60,          # hard cap (default is only 5 min)
    idle_timeout=120,         # 2nd safety net for hung scanners
    tags={"scan_run_id": "sr_01", "batch_id": "b_01"},
)
p = sb.exec("skill-scanner", "scan", "/work/skill", "--format", "json")
p.wait()
print(p.returncode, p.stdout.read()[:200])
sb.terminate(wait=True)   # SIGKILL → sb.returncode == 137
print("sandbox exit:", sb.returncode)
Output
0 {"findings":[{"rule":"curl-pipe-bash","severity":"high", ...
sandbox exit: 137

Lifecycle, Timeouts & Exit Codes

ControlDefaultNotes
timeout300 sHard cap; max 24 h. Beyond that: FS snapshot + new Sandbox.
idle_timeoutnoneActive = running exec, stdin writes, or open Tunnel TCP. Catches hung scanners faster than timeout.
exec(..., timeout=)nonePer-command cap; respected by wait()/poll() since 1.1.0.
Readiness probe—Runs ≤5 min; wait_until_ready() raises modal.exception.TimeoutError (not builtin) and does not terminate the Sandbox.

Exit code semantics

WhereCodeMeaning
p.returncode0 / nScanner's own exit status (e.g. Snyk uses non-zero for "findings present")
sb.returncode137SIGKILL — from terminate(), timeout, or idle_timeout
sb.returncodeOOMDashboard "Exit Reasons" distinguishes memory-limit vs memory-manager kills (Aug 2026)
sb.poll()NoneStill running (fixed in 1.0.1 — used to be 0)

Readiness Probes — Replace the sleep()

Modal polls a check inside the Sandbox every interval_ms (default 100) and fires the Ready event. Two kinds:

ProbeSucceeds whenUse for
Probe.with_tcp(port)Port accepts a connectionMCP server over HTTP/SSE, Jupyter, any server
Probe.with_exec(cmd…)Command exits 0File exists, deps installed, docker info
AgentVetter application
Cisco's mcp-scanner connects to a live MCP server. Boot the server as the Sandbox entrypoint with a TCP probe, call wait_until_ready(), then exec the scanner. No guessed sleep. For stdio servers, use an exec probe on a "ready" marker file written by a wrapper. 
sb = modal.Sandbox.create(
    "npx", "-y", "@modelcontextprotocol/server-everything",
    "sse", "--port", "3001",
    readiness_probe=modal.Probe.with_tcp(3001),
    app=app, image=image, timeout=600,
)
try:
    sb.wait_until_ready()          # ≤ 5 min, then raises
except modal.exception.TimeoutError:
    sb.terminate()                 # probe failure does NOT kill it
    mark_unreachable(scan_run_id)
    raise

p = sb.exec("mcp-scanner", "config",
            "--url", "http://localhost:3001/sse",
            "--format", "json", timeout=240)

Networking: Three Levels of Egress Control

LevelParameterBehaviourMaturity
Full blockblock_network=TrueDrops all outbound; cannot combine with any allowlist or portsGA
IP-range allowlistoutbound_cidr_allowlist=[...]Any protocol to listed CIDRs. (cidr_allowlist is deprecated.)GA
Domain allowlistoutbound_domain_allowlist=[...]TLS/443 only, matched on SNI; Modal resolves the hostname itself. Non-TLS to non-CIDR IPs is blocked. Denials are logged to the Sandbox system stream / App logs.Beta
Runtime swapsb._experimental_set_outbound_network_policy(...)Replace the policy live — e.g. open during npm install, then lock down. Each list type must be set at create time (["*"] / ["0.0.0.0/0"]).Alpha
Inboundinbound_cidr_allowlist=[...]Restricts who can reach Tunnels / Connect TokensGA
Domain fronting caveat (from the docs): two tenants of one CDN share a TLS endpoint, so a Sandbox can send an allowlisted SNI with a different Host header. The allowlist doesn't stop that; a Sidecar proxy that terminates TLS does. ECH connections match only the outer public name.
AgentVetter egress model → Modal mapping
Our spec's static per-scanner domains + dynamic per-run target allowlist maps 1:1 onto outbound_domain_allowlist (e.g. ["api.snyk.io", "*.cisco.com", "api.tessl.io", "github.com"] + the scan target). The "denied-egress logging" fixture gap closes for free: denials land in App logs since 1.5.0.

Credential Isolation: Three Ways to Give a Sandbox an API Key

ApproachHowKey visible inside Sandbox?Constraints
Env-var Secret GAsecrets=[modal.Secret.from_name("snyk")] → $SNYK_TOKENYes — any process can read and exfiltrate itWorks with everything; simplest
Outbound Policy Betamodal.experimental.OutboundPolicy().with_header_replacement(domain, secret, headers) → Modal's proxy terminates TLS and injects Authorization outside the SandboxNo — never in env; CA cert at /etc/modal/sandbox-egress-ca.crtHTTP/1.1 only (no gRPC) · named Secrets only · cannot combine with outbound_domain_allowlist, block_network, CIDR lists, or memory snapshots · ≤25 header values
Sidecar proxy BetaRun a trusted mitmproxy-style container next to the Sandbox; proxy_traffic_via_sidecar relays all 443 traffic to it; Secret injected only in the SidecarNoPre-built images only · Sidecar's own egress policy governs relayed traffic · cannot combine with outbound_domain_allowlist on the main Sandbox
 
policy = (modal.experimental.OutboundPolicy()
  .with_header_replacement(
      domain="api.snyk.io",
      secret=modal.Secret.from_name("snyk"),
      headers={"Authorization": "token $SNYK_TOKEN"})
  .with_header_replacement(
      domain="*.cisco.com",
      secret=modal.Secret.from_name("cisco"),
      headers={"X-Api-Key": "$CISCO_AI_DEFENSE_API_KEY"}))

sb = modal.Sandbox.create(app=app, image=image,
        _experimental_outbound_policy=policy)
AgentVetter open decision — this is the one to make
Our spec deferred credential isolation to "Modal's built-in Secret handling". That is the env-var row — the scanned (untrusted) MCP server shares an environment with SNYK_TOKEN. The Outbound Policy row fixes that, but it is mutually exclusive with the domain allowlist we also want. Options: (a) env Secrets + domain allowlist (today's posture, leak-prone), (b) Outbound Policy, lose the allowlist (every domain open), (c) Sidecar proxy doing both allowlist and injection — most work, only option that gives both. Snyk's CLI may also need the token via env, not header; verify hands-on per scanner.

Sidecars Beta

Extra containers on the same host, bridged by name (main, web, …). Share the Sandbox's CPU/memory. Up to 250 per Sandbox.

Patterns: agent harness ↔ tool executor split; credential-injecting proxy; Redis/DB next to the app; HTTPS inspection via proxy_traffic_via_sidecar.

Limits: pre-built images only, no stdio on entrypoint, no memory snapshot, VM runtime needs a fixed memory reserve.

AgentVetter post-MVP
The deferred "deeper observability layer" (file/process monitoring beyond egress denials) is a Sidecar job: a mitmproxy sidecar logs every outbound request the scanned MCP server makes, with full URL + body, into Supabase.

Which Sandbox Configuration?

Does the workload need Docker, FUSE, or nested cgroups?
Yes → runtime="vm" (no GPU)
No → gVisor (default; GPU OK)
↓
Does the code need network at all?
No → block_network=True (Cisco config YARA scan)
Known hosts → outbound_domain_allowlist (+ CIDR for non-TLS)
Open then lock → ["*"] + runtime policy swap (alpha)
↓
Does it call an authenticated external API?
Trusted code → env Secret
Untrusted, no allowlist needed → Outbound Policy
Untrusted + allowlist → Sidecar proxy
↓
Will it outlive 24 h or need reuse?
Ephemeral job → timeout + idle_timeout, terminate
Session → FS/Directory snapshot keyed by session ID
Exclusive per resource → name= (named Sandbox)

AgentVetter open decision (Aug 4)
Deployed Apps retry crashed containers with backoff indefinitely; ephemeral Apps stop at a failure-rate threshold. If the fan-out orchestrator is deployed, a broken scanner adapter can crash-loop outside Supabase's view. Decide: ephemeral modal run from the CLI (current), or deployed + retries=0 + explicit status writes.

Section 05

Engineering Deep Dives

What Modal has published about how the thing works — and how to read their comparison guides

Under the Hood & Reading the Vendor Guides

Scaling to 1M concurrent Sandboxes
The engineering post behind V2: a rebuilt scheduler and filesystem path that pushed creation rates past 20/s per workspace and demonstrated a million concurrent Sandboxes. This is why create() now blocks until scheduled — placement became the real cost.
gVisor vs microVMs
Modal's isolation story: gVisor intercepts syscalls in userspace (fast start, dense packing); competitors (E2B, Vercel) use Firecracker microVMs. Modal added a KVM "vm" runtime in 1.6 for workloads that need a real kernel — so you now choose per Sandbox.
SWE-bench upstream
Modal contributed a --modal flag to SWE-bench; the 500-task Verified set runs in ~7 minutes. Useful precedent for AgentVetter: a benchmark harness that fans out one Sandbox per task is a solved pattern.

Security & compliance posture

SOC 2 Type II (all plans) · HIPAA via BAA (Enterprise) · Audit logs (Enterprise) · Data residency and region selection · Customer-supplied encryption keys (alpha) · Restricted Functions / private Environments · Sandboxes cannot touch other workspace resources by default.

The "Best Sandboxes for X in 2026" series

Modal's resources section carries ~10 vendor-authored comparison guides (tool-calling agents, RL, notebooks, IDEs, SWE-bench…). They're accurate about Modal's own limits (24 h, 50k–100k concurrency, GPU list) and reasonably fair on E2B/Daytona/Vercel/Cloudflare — but every one concludes "Modal stands out". Treat as a feature checklist, not a verdict.
